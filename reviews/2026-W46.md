<details><summary><b>Answers</b> (try first)</summary>

1. The new member's join triggers a rebalance and every member rejoins, but in round one nobody revokes anything. The assignor computes the new mapping, and only the partitions that must move are revoked, then assigned in a second round. Two rounds are needed because if the new owner got the partition while the old owner was still processing it, two members would read it at once and uncommitted work could be duplicated or conflict. The revoke has to complete (and offsets be committed) first.
2. Nginx's connect to a freshly restarted pod was refused (`connect() failed (111: Connection refused) while connecting to upstream`) because the pod was registered as an upstream before it was listening. The request never reached the app, so app metrics show no 5xx. A 504 means the upstream was up but did not answer within the gateway's timeout (`upstream timed out (110...)`, e.g. `proxy_read_timeout`), and the app may even finish the request later.
3. PID 1 adopts orphans but only reaps them if it calls `wait()`; an app that handles SIGTERM but never waits on adopted children leaks zombies, and trapping TERM with `wait` in a shell script doesn't reap helpers either. `--init` (tini) runs as PID 1, forwards signals to your app, and reaps zombies.
4. A flag-store outage or a missing or renamed key makes the call site fall back to the hardcoded default, which silently turns the new path on for 100% of traffic and bypasses the staged rollout. Defaults should be the safe (usually old) behavior, and the failure path should be tested with the provider unreachable.
5. As liveness, all pods fail at the same moment, are killed and restart together, then reconnect together and hammer the recovering database, turning a partial outage into a full one. As readiness, pods are only removed from Service endpoints, with no restarts, so users get 503s from the Service while the database recovers, and pods return once it is back. Keep liveness to "can this process make progress".
