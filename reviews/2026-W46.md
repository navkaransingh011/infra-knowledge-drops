## This week's hands-on

Start a second consumer in the same group and describe again.

You're done when you can say which partitions moved to the second consumer, and that the first consumer kept the rest without a full revoke (check its client log for the revoke of only the moved partitions). Bonus: repeat with an eager assignor (e.g. `RangeAssignor`) and compare the logs.

<details><summary><b>Answers</b> (try first)</summary>

1. Membership changes (join/leave/timeout/partition-count change), the coordinator starts a rebalance, and every member must rejoin. Under eager, each member first revokes all its partitions, then rejoins and waits for the new assignment. The whole group stops consuming during that window, even for partitions that return to the same member.
2. Rolling restarts trigger a rebalance per pod, and with an eager assignor each one pauses all 12 pods, causing the lag sawtooth. Duplicates occur because uncommitted work on revoked partitions is re-read by the new owner. Switch to `CooperativeStickyAssignor` and add static membership (`group.instance.id`) so a quickly restarted pod keeps its identity and partitions; also commit offsets in `onPartitionsRevoked`.
3. Heartbeats run on a separate thread (KIP-62), so a stuck application thread keeps heartbeating and `session.timeout.ms` never fires. Only `max.poll.interval.ms` catches it: if `poll()` isn't called in time, the client leaves the group. Fix the cause by reducing `max.poll.records`, speeding processing, or raising `max.poll.interval.ms`.
4. All members must support the protocol, so changing everyone at once on a live group is not a plain config flip. Do a rolling change that lists both assignors first, then a second rolling change that removes the old one.
5. `session.timeout.ms` (heartbeat thread) detects process death or lost connectivity. `max.poll.interval.ms` (application `poll()` loop) detects stalled progress while the process is still alive.

</details>
