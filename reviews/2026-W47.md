## This week's hands-on
**Terraform address moves (INF-092), 15 minutes.** Needs only Terraform or OpenTofu and the `local` provider.

1. In a temp directory, create a `local_file` resource named `greeting`, then `terraform init && terraform apply -auto-approve`.
2. Run `terraform state list` and `terraform state show local_file.greeting` to see the ID and attributes recorded.
3. Rename the resource to `renamed` in code, with no `moved` block, and run `terraform plan`.
4. Add a `moved { from = local_file.greeting  to = local_file.renamed }` block and run `terraform plan` again.
5. Bonus: delete `terraform.tfstate` and plan again to see what it wants to do.

**You're done when:** the first plan shows 1 to add, 1 to destroy, the second shows the address move with no infrastructure change, and you can say what the bonus plan does and why.

## Connect it to work
Think of a pipeline or system you run where delivery is at-least-once (a queue consumer, a CI webhook, a Terraform apply retried by automation). Where is the gap between the side effect and the ack, and what would you check to confirm a duplicate or a lost event is harmless there?

<details><summary><b>Answers</b> (try first)</summary>

1. The client does two small `write()`s. The first leaves immediately. The second is small while data is unacked, so Nagle holds it. The server has only half a request, so it has no response to piggyback an ACK on and its delayed-ACK timer (~40 ms on Linux) is what releases the deadlock. Nagle is a sender behavior, so `TCP_NODELAY` must be on the socket doing the small writes. If the server's response is the stalled part, setting it on the client does nothing. The better fix is a single `write()` of the whole request.
2. Terraform decides create vs destroy from state membership by address. State still maps the old address to the DB's ID and nothing maps the new address, so old is destroyed and new is created. Fix it by declaring the move, with a `moved` block (Terraform ≥ 1.1) or `terraform state mv`. The plan should then show no changes.
3. The token `PUT` response has an IP TTL equal to the hop limit. A container on a bridge network adds a hop, so with a limit of 1 the response is dropped. The client sees a timeout, the SDK falls through its credential chain, and requests are never signed, hence no CloudTrail denials. The usual fix is raising `HttpPutResponseHopLimit` to 2 (or host networking), but that lets any container on the node obtain the node's role credentials. Per-workload identity is preferred on shared nodes.
4. FIFO dedup covers only the producer-to-broker hop. The consumer's side effect (the email) happens before the ack, so a pod killed in between leaves the message to be redelivered. Effectively-once is at-least-once plus an idempotent operation: a unique constraint on `order_id` before sending, or an idempotency key passed to the partner API.
5. A leaked authorized token: encryption at rest does not help, since storage decrypts for any authorized caller, and TLS only protects the download from sniffers. Least privilege, short-lived credentials, access alerts and KMS key policies are the controls. For the backdoored image: signature verification at admission rejects it because the new digest has no signature from the build workflow, provided the policy pins the exact signer identity and issuer. At-rest and in-transit encryption protect segments of the data's path. Signing protects who produced the artifact, not where it travels.

**Bonus (INF-134).** The resolver tries `payments.<own-ns>.svc.cluster.local` first. That matches only in the namespace where the Service lives, and from another namespace it gets NXDOMAIN. From the same namespace it resolves. `payments.billing` is tried as `payments.billing.<ns>.svc.cluster.local` (fails), then `payments.billing.svc.cluster.local` (succeeds if the Service is in `billing`), so it works from both namespaces.
