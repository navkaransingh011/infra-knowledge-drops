# Container vs virtual machine isolation

`INF-109` · Docker and containers › Container fundamentals · Difficulty 1/3 · ~6 min

> **Why this matters:** "It's in a container, so it's isolated" is true in a much weaker sense than "it's in a VM". Knowing exactly where the boundary sits decides how you handle untrusted code, kernel patching, and noisy-neighbor incidents.

## The moving parts
- **Kernel**: the one program that owns hardware, memory, and every system call. Everything else asks it for services.
- **Hypervisor**: software (KVM, Xen, Hyper-V) that carves hardware into virtual machines, each running its *own* guest kernel.
- **Namespaces** (Linux): kernel feature that gives a process its own *view* of a resource: PIDs, mounts, network, hostname, IPC, users, cgroups.
- **cgroups**: kernel feature that *limits and accounts* for resources (CPU, memory, I/O, PIDs) per group of processes.
- **Syscall filters / capabilities / LSMs**: seccomp, dropped capabilities, AppArmor/SELinux. They narrow which kernel entry points a process may use.

## How it works
A VM and a container draw the boundary in different places:

```
 VM:                               Container:
 app  app                          app   app
 guest kernel (per VM)             ──namespaces/cgroups/seccomp──
 ─────virtual hardware────        HOST KERNEL (shared)
 hypervisor                        hardware
 hardware
```

1. A VM boots a complete guest kernel. The app's syscalls go to *that* kernel. To escape, it must first compromise the guest kernel, then cross the hypervisor's much smaller interface (virtual devices, VM exits).
2. A container is an ordinary Linux process started with namespaces, cgroup membership, and filters applied. There is no second kernel. Its syscalls go straight into the **host kernel**.
3. Namespaces change what the process can *see* (its own PID 1, its own `eth0`), and cgroups cap what it can *consume*. Neither makes the kernel a different kernel.
4. So the isolation boundary is the host kernel's syscall interface plus its correct enforcement of namespaces. A kernel bug reachable from allowed syscalls can break out of every container on that host at once.
5. Consequences follow directly: containers start in milliseconds (no boot), have near-zero memory overhead, and must run a kernel-compatible userland (a Linux container needs a Linux kernel). VMs cost more but can run a different OS and have a narrower attack surface.

## In production
A team runs a multi-tenant CI service where customers submit build scripts, each in its own Docker container on shared nodes. A customer's build hits a bug in a kernel code path that its syscalls can reach, and the node's kernel panics; every container on the node, belonging to different customers, dies together. Another day, a build allocates memory aggressively and the node logs `Memory cgroup out of memory: Killed process ...` for that container only: cgroups worked as designed there.

The first incident shows the shared-kernel blast radius; the second shows resource isolation holding. The fix for the trust issue was not tuning Docker flags alone but moving untrusted builds into a stronger boundary: a microVM-based runtime (e.g. Kata Containers or Firecracker) or a user-space kernel (gVisor), so each tenant gets its own kernel or its own syscall surface. Trusted internal workloads stayed on plain containers.

## The gotcha
`--privileged`, mounting `/var/run/docker.sock`, or adding broad capabilities (e.g. `CAP_SYS_ADMIN`) quietly removes much of the isolation, since the process can then reconfigure the very kernel features that confine it. Also, `uname -r` inside a container reports the **host's** kernel version: a container image cannot carry its own kernel, so "this image needs kernel 6.x features" is a property of the *node*, not the image. And Docker's default seccomp profile is an allow-list tuned for compatibility, not a guarantee against kernel bugs.

## Try it
```bash
uname -r                                  # host kernel
docker run --rm alpine uname -r           # same string: shared kernel
docker run --rm alpine ps                 # sees only its own processes (PID namespace)
docker run --rm -m 64m alpine sh -c 'cat /sys/fs/cgroup/memory.max'  # cgroup v2: 67108864
sudo unshare --pid --fork --mount-proc ps # a "container" without Docker: just namespaces
```
Look for: identical kernel version in host and container, but a tiny process list inside. (`memory.max` path assumes cgroup v2; on cgroup v1 hosts it differs.)

## Think about it
A container and its host report the same kernel version, yet `ps` inside shows only a few processes while the host sees them all, including the container's. Using the PID namespace, explain how one process can have two different PIDs at once, and what that implies about whether "the container" is a real object the kernel knows about.
