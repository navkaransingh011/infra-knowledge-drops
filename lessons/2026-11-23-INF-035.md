# TCP keepalive vs application keepalive

`INF-035` · Networking and protocols › TCP and UDP · Difficulty 2/3 · ~6 min

> **Why this matters:** A peer that vanishes without a FIN or RST (a crashed host, a dropped NAT mapping, a pulled cable) leaves your side believing the connection is healthy. The result is hung workers, leaked connections and "stuck" clients that only recover hours later.

## The moving parts
- **TCP connection state:** each endpoint's kernel holds state for a connection. If the peer disappears silently, nothing tells your kernel to discard it.
- **TCP keepalive (kernel):** an optional per-socket feature (`SO_KEEPALIVE`). After the connection has been idle for a while, the kernel sends empty probe segments and expects an ACK. The application is not involved.
- **Application keepalive (heartbeat):** a message defined by your own protocol (HTTP/2 PING, gRPC keepalive, a database `SELECT 1`, WebSocket ping/pong, AMQP heartbeats). It travels as ordinary data through the application.
- **`TCP_USER_TIMEOUT`:** a Linux socket option. It sets how long transmitted data may stay unacknowledged before the kernel aborts the connection.

## How it works
Linux defaults for keepalive (checked with `sysctl` on Linux 6.x; they have long been the same):

```
net.ipv4.tcp_keepalive_time   = 7200   # idle seconds before the first probe
net.ipv4.tcp_keepalive_intvl  = 75     # seconds between probes
net.ipv4.tcp_keepalive_probes = 9      # unanswered probes before giving up
```

The causal chain:
1. Keepalive is **off by default**. A program must call `setsockopt(SO_KEEPALIVE)`. The sysctls above only supply defaults for sockets that opted in. Per-socket overrides are `TCP_KEEPIDLE`, `TCP_KEEPINTVL` and `TCP_KEEPCNT`.
2. Once a socket is opted in and idle for `time` seconds, the kernel sends a probe, an ACK segment carrying a sequence number the peer has already acknowledged. A live peer's stack answers with an ACK.
3. If the peer answers, the idle timer restarts. If it replies RST (the peer rebooted and has no such connection), the connection is torn down at once. If there is no reply, the kernel retries every `intvl`.
4. After `probes` failures the kernel closes the socket. Your next `read`/`write` fails with `ETIMEDOUT`.
5. With the defaults, detection takes 7200 + 9×75 = **7875 s, about 2.2 hours**.

The key limitation: keepalive only proves that the **remote kernel's TCP stack** is alive. The probe is answered without the application ever running. A peer whose process is deadlocked, or whose event loop is blocked, still ACKs every probe. Only an application heartbeat passes through the application and tests it.

```
 app A ──heartbeat req──▶ ... kernel B ──▶ app B   (tests the whole path, including B's code)
 kernel A ──keepalive probe──▶ kernel B            (tests only B's TCP stack and the network)
```

Keepalive also has a second effect: periodic traffic refreshes **idle timers in middleboxes** (NAT, conntrack, load balancers). If their timeouts are shorter than the first probe, the default 2-hour idle time never helps.

## In production
A service holds long-lived connections to a database through a cloud load balancer. During a failover, the DB host disappears with no FIN or RST. The app's pool shows connections "in use". Request threads block, p99 latency climbs, and the pool is exhausted. `ss -tno` shows the sockets as `ESTAB` with no `timer:(keepalive,...)` entry, because the driver never enabled `SO_KEEPALIVE`. Queries on those connections fail with `ETIMEDOUT` only after the kernel's retransmission limit, minutes later. Idle connections would have been found after about 2 hours.

Fixes, layered:
- Enable keepalive with short per-socket values (for example 30 s idle, 10 s interval, 3 probes) so dead peers are found in about 60 s.
- Set `TCP_USER_TIMEOUT` so a connection with unacknowledged data is aborted promptly.
- Add an application-level health check or heartbeat that detects a hung peer, which keepalive cannot.

## The gotcha
**Keepalive does not protect a connection that is actively sending data.** Probes are sent only when the connection is idle. If you have unacknowledged data outstanding, the kernel is in retransmission mode, and the limit is governed by retransmission timeouts (`tcp_retries2`, default 15, which gives roughly 15 minutes or more on Linux), not by the keepalive settings. Keepalive timers do not decide when to give up there. To bound that case, use `TCP_USER_TIMEOUT`, which Linux documents as interacting with keepalive: when both are set, `TCP_USER_TIMEOUT` overrides the keepalive probe count for deciding when to drop.

Relatedly, tuning only the sysctls changes nothing for programs that never enabled `SO_KEEPALIVE`.

## Try it
Set the options on a socket and read them back:

```python
import socket
s = socket.socket()
s.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPIDLE, 30)
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPINTVL, 10)
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPCNT, 3)
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_USER_TIMEOUT, 60000)  # ms
print([s.getsockopt(socket.IPPROTO_TCP, o) for o in
       (socket.TCP_KEEPIDLE, socket.TCP_KEEPINTVL, socket.TCP_KEEPCNT, socket.TCP_USER_TIMEOUT)])
```

Expect `[30, 10, 3, 60000]`. Then run `sysctl net.ipv4.tcp_keepalive_time net.ipv4.tcp_keepalive_intvl net.ipv4.tcp_keepalive_probes` to see the system defaults. On an established connection, `ss -tno` (iproute2) shows a `timer:(keepalive,...)` field when keepalive is active.
