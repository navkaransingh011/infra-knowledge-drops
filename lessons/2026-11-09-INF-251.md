# Kafka consumer group rebalances: eager vs cooperative

`INF-251` · Distributed systems and messaging › Consumer lag and backpressure · Difficulty 2/3 · ~7 min

> **Why this matters:** A single slow consumer can make a whole group stop reading for seconds, then repeat it in a loop. Lag spikes in a Kafka service often come from rebalances rather than from load.

## The moving parts
- **Consumer group:** consumers sharing a `group.id`. Each partition of a subscribed topic is read by exactly one member at a time.
- **Group coordinator:** a broker that tracks group membership and hands out partition assignments.
- **Heartbeat thread:** a background client thread that tells the coordinator "I'm alive". If heartbeats stop for longer than `session.timeout.ms`, the member is removed.
- **`poll()` loop:** your application thread. If it doesn't call `poll()` again within `max.poll.interval.ms`, the client leaves the group, even though heartbeats are still flowing.
- **Assignor:** the strategy (`partition.assignment.strategy`) that decides which member gets which partitions.

## How it works
1. Membership changes: a consumer joins, leaves, is timed out, or the topic's partition count changes.
2. The coordinator starts a rebalance. Every member must rejoin the group.
3. **Eager protocol (Range, RoundRobin, Sticky assignors):** each member first *revokes all its partitions*, then rejoins. The whole group stops consuming until the new assignment arrives (the "stop-the-world" pause), even for partitions that end up back on the same member.
4. **Cooperative protocol (`CooperativeStickyAssignor`, KIP-429, Kafka 2.4+):** members keep their partitions through the first round. The assignor computes the new mapping, and only the partitions that actually move are revoked, in a second round. Unaffected partitions keep being consumed.

```
Eager:        [revoke ALL] ---- pause ---- [receive new assignment]
Cooperative:  keep all -> [revoke only moved ones] -> [receive them elsewhere]
```

Because uncommitted work on a revoked partition may be re-read by the new owner, revocation is also where you should commit offsets (`onPartitionsRevoked`).

## In production
A payment-events consumer group runs 12 pods on Kubernetes. Each record triggers a slow downstream call. During a deploy, rolling restarts trigger a rebalance per pod. Symptoms: consumer lag graphs show sawtooth spikes; client logs repeat lines like "Revoke previously assigned partitions" and "(Re-)joining group"; the same messages are processed twice around each spike. With an eager assignor, every restart pauses all 12 pods. Switching to `CooperativeStickyAssignor` and adding static membership (`group.instance.id`, so a quickly restarted pod keeps its identity and partitions) reduces the pauses to the partitions that actually move.

A second pattern: a batch of slow records makes processing exceed `max.poll.interval.ms`. The client logs that the poll interval was exceeded, the member is kicked, a rebalance runs, and the same slow batch is handed to another member, which also fails. Fix: reduce `max.poll.records`, speed up processing, or raise `max.poll.interval.ms`.

## The gotcha
Raising `session.timeout.ms` does not fix slow processing. Since the heartbeat runs on its own thread (KIP-62, Kafka 0.10.1+), a consumer with a stuck application thread keeps heartbeating happily. Only `max.poll.interval.ms` catches it. The two timers detect different failures: process death versus stalled progress. Also, switching assignors is not a plain config flip on a live group: all members must support the protocol, so do a rolling change that lists both assignors first, then removes the old one.

## Try it
```bash
# Requires a local broker (e.g. a throwaway Docker container) and Kafka CLI tools
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic demo --partitions 6
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic demo --group g1 \
  --consumer-property partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
# Start a second consumer in another terminal, then inspect:
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group g1
```
Look at how partitions are split between members, and which consumer's partition list changed when the second one joined.

## Think about it
In a cooperative rebalance, why does the protocol need two rounds instead of one? What could go wrong if the new owner of a moving partition received it in the same round that the old owner was told to revoke it?
