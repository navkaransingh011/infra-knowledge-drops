# Transaction ID wraparound and freezing

`INF-254` · Databases and storage engines › PostgreSQL maintenance · Difficulty 2/3 · ~7 min

> **Why this matters:** A PostgreSQL database that stops accepting writes with "database is not accepting commands to avoid wraparound data loss" is a full outage. It is almost always the end of a slow, silent failure: something stopped autovacuum from freezing old rows, and nobody watched the one number that shows it.

## The moving parts

- **Transaction ID (XID):** a 32-bit counter. Every transaction that writes gets the next one. It is stamped on each row version as `xmin` (creator) and `xmax` (deleter) so MVCC can decide who sees what.
- **Circular comparison:** XIDs are compared modulo 2³². For any XID, about 2 billion IDs count as "in the past" and about 2 billion as "in the future". Visibility depends on this split.
- **Freezing:** `VACUUM` marks an old row version as frozen. A frozen row is treated as older than every XID, so its `xmin` no longer needs to be compared.
- **`relfrozenxid` / `datfrozenxid`:** per-table and per-database records of "every XID older than this is already frozen in this table or database". `age(datfrozenxid)` is how many XIDs have been consumed since.
- **Autovacuum:** the background worker that runs `VACUUM`, including the anti-wraparound kind that cannot be cancelled by lock conflicts the way ordinary runs can.

## How it works

```
 XID space (circular, 2^32)
        oldest unfrozen xid
              |<--- ~2^31 "past" --->|current|<--- ~2^31 "future" --->|
```

1. Each write transaction consumes one XID, so the counter keeps advancing.
2. A row inserted at XID 100 looks "in the past" for the next ~2 billion transactions.
3. After about 2³¹ more XIDs, the same XID 100 would flip to looking like the future. The row would suddenly become invisible: committed data apparently vanishes.
4. To prevent this, `VACUUM` rewrites old tuples as frozen before they get that old. Freezing is also what lets the table's `relfrozenxid` advance.
5. Autovacuum is forced to start an anti-wraparound vacuum on a table once `age(relfrozenxid)` exceeds `autovacuum_freeze_max_age`. This happens even if autovacuum is otherwise disabled.
6. If freezing still doesn't advance, the server logs warnings as the limit nears. Then, very close to the limit (a few million XIDs away), it refuses new XID assignments and only allows a manual `VACUUM` in single-user mode or equivalent recovery.

Defaults, verified on PostgreSQL 16:

| Setting | Default |
|---|---|
| `autovacuum_freeze_max_age` | 200,000,000 (needs restart to change) |
| `vacuum_freeze_table_age` | 150,000,000 (a normal vacuum becomes an aggressive, full-scan one) |
| `vacuum_freeze_min_age` | 50,000,000 (rows older than this get frozen when vacuum visits them) |
| `vacuum_failsafe_age` | 1,600,000,000 (vacuum drops cost-delay throttling and skips index cleanup to finish) |

The 200 million trigger sits at about a tenth of the 2 billion budget, so there is a large safety margin by design. A healthy cluster never gets near the hard stop.

## In production

A SaaS team runs a 4 TB Postgres 16 primary with a busy write path, roughly 3,000 TPS. Their dashboards cover CPU, connections and replication lag. One Monday the log shows:

```
WARNING:  database "app" must be vacuumed within 38000000 transactions
HINT:  To avoid XID assignment failures, execute a database-wide VACUUM in that database.
```

Checking the age:

```sql
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
-- app | 2109000000
```

At 3,000 TPS that is roughly 12 days of runway, not months. Autovacuum had been starting anti-wraparound workers on the big tables, but each run was cancelled or made no progress. The cause was a logical replication slot for a decommissioned consumer. Its `xmin`/`catalog_xmin` pinned the horizon, so vacuum could not freeze rows newer than that point and `relfrozenxid` never advanced.

Fix: find what holds the horizon, remove it, then let vacuum catch up.

```sql
SELECT slot_name, active, xmin, catalog_xmin FROM pg_replication_slots;
SELECT pid, state, xact_start, backend_xmin FROM pg_stat_activity
 WHERE backend_xmin IS NOT NULL ORDER BY age(backend_xmin) DESC;
SELECT gid, prepared FROM pg_prepared_xacts;
```

They dropped the dead slot with `pg_drop_replication_slot(...)`. Then they ran `VACUUM (FREEZE, VERBOSE)` on the oldest tables, found via `age(relfrozenxid)` in `pg_class`. Afterwards they added an alert on `age(datfrozenxid)` at 1 billion.

## The gotcha

Raising `autovacuum_freeze_max_age` or tuning autovacuum harder does not help when the horizon is pinned. Freezing can only freeze rows that are older than the oldest XID anything might still need: the oldest open transaction, a prepared transaction, a replication slot, or (when `hot_standby_feedback` is on) a long query on a standby. Vacuum can run flat out, finish "successfully", and `relfrozenxid` still doesn't move. The symptom is autovacuum workers constantly busy on the same tables while `age()` keeps climbing, so the problem looks like a throughput problem when it is really a blocker.

The second trap is that the wraparound-prevention vacuum on a huge, mostly static table is expensive. It must scan pages not yet marked all-frozen in the visibility map, and it starts at a moment you don't choose. Scheduled manual `VACUUM (FREEZE)` during quiet hours spreads that cost out.

## Try it

Throwaway cluster, run as a non-root user:

```bash
initdb -D /tmp/xiddemo && pg_ctl -D /tmp/xiddemo -o '-p 5544' -l /tmp/xiddemo.log start
psql -p 5544 postgres -c "SELECT datname, age(datfrozenxid) FROM pg_database;"
psql -p 5544 postgres -c "CREATE TABLE t AS SELECT g FROM generate_series(1,1000) g;
  SELECT relname, relfrozenxid, age(relfrozenxid) FROM pg_class WHERE relname='t';"
# Hold the horizon back in a second session:  BEGIN; SELECT txid_current();  (leave open)
psql -p 5544 postgres -c "VACUUM (FREEZE) t; SELECT age(relfrozenxid) FROM pg_class WHERE relname='t';"
```

Look for: with the open transaction, `relfrozenxid` stays behind its XID. Commit or close that session, rerun `VACUUM (FREEZE)`, and it advances. Stop with `pg_ctl -D /tmp/xiddemo stop`.

## Think about it

A table is insert-only, so autovacuum's dead-tuple thresholds never trigger on it, yet its `age(relfrozenxid)` still keeps growing. What eventually makes vacuum run on it, why does that first run suddenly rewrite a huge number of pages, and what would you change to make that work happen earlier and in smaller pieces?
