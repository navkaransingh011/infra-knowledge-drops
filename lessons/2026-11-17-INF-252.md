# Nagle's algorithm and delayed ACK interaction

`INF-252` · Networking and protocols › TCP · Difficulty 2/3 · ~6 min

> **Why this matters:** A service that answers in 1 ms locally suddenly shows a hard floor of ~40 ms (or 200 ms) per request over a real network, with idle CPU and a healthy network. Two well-intentioned TCP optimizations, each harmless alone, are waiting on each other.

## The moving parts
- **Segment and MSS**: TCP cuts the byte stream into segments. MSS (maximum segment size) is the largest payload per segment, typically ~1448 bytes on Ethernet.
- **ACK**: the receiver's acknowledgement of bytes received. It can ride on data going the other way.
- **Nagle's algorithm** (RFC 896, required-to-offer behavior in RFC 1122 §4.2.3.4): it exists to stop "tinygram" floods (e.g. one packet per keystroke). Rule: if there is unacknowledged data in flight, hold new *small* data in the send buffer until either the ACK arrives or enough data accumulates to fill an MSS.
- **Delayed ACK** (RFC 1122 §4.2.3.2): it exists to cut ACK-only packets. The receiver may wait before ACKing, hoping to piggyback the ACK on response data. The delay must be under 500 ms, and an ACK must go out for at least every second full-sized segment.
- **TCP_NODELAY**: socket option that turns Nagle off for that socket.

## How it works
Each side is polite on its own. The trouble is the sender waits for an ACK, and the receiver waits for more data before sending it.

```
client                                   server
  │── write #1: header (small) ─────────►│  server app needs the body to reply,
  │                                      │  kernel delays the ACK ("maybe data to piggyback")
  │  write #2: body (small)              │
  │  Nagle: #1 unacked → HOLD #2         │
  │         ......... ~40 ms .........   │
  │◄────────────── delayed ACK ──────────│  timer fires
  │── write #2 released ────────────────►│
  │◄── response (+ACK) ──────────────────│
```

The causal chain:
1. The client app does two small `write()`s for one logical request (header, then body).
2. The first goes out immediately (nothing is in flight). The second is small and data is unacked, so Nagle holds it.
3. The server has only half a request. It cannot respond, so there is no data to piggyback an ACK on.
4. The server kernel's delayed-ACK timer is the only thing that breaks the deadlock. On Linux the timer is short (minimum ~40 ms, ceiling ~200 ms, adapting to the connection); other stacks differ (Windows and some BSD-derived stacks are commonly cited at 200 ms).
5. The ACK finally arrives, Nagle releases write #2, and the request completes. Added latency is the ACK delay, per request, regardless of bandwidth or RTT.

The pattern is "write-write-read": two small writes, then wait for a reply. A single `write()` of the whole request, or a full-MSS-sized write, avoids it. (Linux implements a Minshall variant of Nagle that holds data only when a previously sent *small* segment is unacked, which is why the pattern needs a small first write.)

## In production
A Python service calls an internal RPC server with a hand-rolled protocol: `sock.sendall(header)` then `sock.sendall(payload)`, then `recv()`. In the dev VM, p50 was 2 ms. After deployment across two hosts, every call's p50 sat at ~41 ms and p99 near 45 ms, a suspiciously flat floor. CPU on both ends was under 10%, and `ping` RTT was 0.3 ms.

A `tcpdump -ttt` on the server showed the client's header segment, then a gap of ~40 ms, then a bare ACK from the server, then immediately the client's payload segment. The gap sat between a data segment and a pure ACK, which is the delayed-ACK signature, and the payload only left after that ACK, the Nagle signature.

Fix options, in order of preference:
1. Send the request in one `write()`/`sendall()` (build the buffer first, or use `writev`/`sendmsg`).
2. Set `TCP_NODELAY` on the client socket. The p50 dropped to ~2 ms.
3. Only as a last resort, `TCP_QUICKACK` on the receiver (see the gotcha).

## The gotcha
**`TCP_NODELAY` on one side does not always fix it, and `TCP_QUICKACK` does not stay set.** Nagle is a *sender* behavior, so the option must be set on the socket that is doing the small writes. If the stall is in the server's response (server writes header, then body), setting it on the client does nothing. Many libraries (Go's `net` package, for example, enables `TCP_NODELAY` by default) already do this, so a stack mixing languages can have it in one direction only.

`TCP_QUICKACK` is not a permanent mode: per tcp(7), the kernel can switch back to delayed-ACK behavior, so you must re-set it after reads. That is why it is a fragile fix and `TCP_NODELAY` plus fewer writes is preferred.

Also, `TCP_NODELAY` is not free: with it on, a loop of tiny `write()`s turns into a flood of tiny packets. Fix the write pattern first.

## Try it
Check whether a socket has Nagle disabled and watch for the delayed-ACK shape in a capture:

```bash
# On a throwaway container/VM: capture a small-request client/server pair
sudo tcpdump -i any -ttt -nn 'tcp port 9000'
# look for: data segment ... ~40 ms gap ... bare ACK ... then the next data segment
```

```python
import socket
s = socket.create_connection(("127.0.0.1", 9000))
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)   # disable Nagle on this sender
print(s.getsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY))  # 1 = Nagle off
```

Note: on loopback you often will not reproduce the stall. I tried a write-write-read loop on loopback in a Linux 6.18 sandbox and saw no difference (~0.02 ms either way), so test across two hosts or VMs, or a network namespace with added latency, and compare latency with and without `TCP_NODELAY`.
