# Linux page cache and available memory

`INF-009` · Linux and operating systems › Memory and CPU · Difficulty 2/3 · ~6 min

> **Why this matters:** "Free memory is 1%!" is one of the most common false alarms in Linux operations, and the opposite mistake, ignoring memory that is *not* reclaimable, is how nodes get OOM-killed while dashboards look fine. Knowing which column to trust avoids both.

## The moving parts
- **Page cache:** RAM the kernel uses to hold copies of file contents (and writes waiting to go to disk). It exists because RAM is orders of magnitude faster than disk, so reading a file twice should hit disk once.
- **Buffers:** a small cache of block-device metadata. Today it is usually tiny and is folded into "buff/cache" by `free`.
- **Clean vs dirty pages:** a clean page matches what is on disk and can be dropped instantly. A dirty page has been modified in memory and must be written back first.
- **Reclaim:** the kernel's process of freeing pages when memory is short, by dropping clean cache, writing back dirty cache, or swapping anonymous memory.
- **Anonymous memory:** heap, stack and other memory with no file behind it (what your processes "allocate"). It can only be freed by the process exiting, or by swap if enabled.
- **`MemAvailable`:** a field in `/proc/meminfo` (Linux ≥ 3.14) that is the kernel's *estimate* of how much memory could be given to new workloads without swapping. `free` shows it as `available`.

## How it works
1. A process calls `read()` on a file. The kernel reads the blocks from disk into page-cache pages, then copies to the process.
2. Nothing evicts those pages yet. The kernel has no reason to leave RAM empty, so cache grows to fill otherwise-idle memory.
3. `MemFree` shrinks, and `buff/cache` grows. This is normal and desirable.
4. When an allocation needs pages and free memory is low, reclaim drops the least-recently-used *clean* cache pages first. Cost: a future re-read goes to disk.
5. `MemAvailable` is computed as roughly: `MemFree` + the reclaimable part of page cache + reclaimable slab (`SReclaimable`), minus safety margins (the kernel keeps low watermarks and won't count the last bit of cache that is hot).

```
MemTotal
├─ used (anonymous: your processes)        <- not reclaimable without swap
├─ buff/cache
│    ├─ clean file pages                   <- reclaimable, cheap
│    ├─ dirty file pages                   <- reclaimable after writeback
│    └─ Shmem (tmpfs, shared mem)          <- NOT freed by dropping cache
└─ free                                    <- truly unused
available ≈ free + reclaimable cache + SReclaimable − margins
```

So `free` answers "how much is unused", while `available` answers the operationally useful question "how much can I allocate before trouble".

## In production
A team runs a log-processing node with 16 GiB RAM. A monitoring alert fires: "memory used 97%", computed as `1 - MemFree/MemTotal`. Engineers log in and see:

```
              total   used   free  shared  buff/cache  available
Mem:           15Gi   2.1Gi  310Mi  40Mi      12Gi       13Gi
```

The service is healthy, and p99 latency is fine. A nightly job simply scanned many GiB of logs, filling the cache. Someone "fixes" it by running `echo 3 > /proc/sys/vm/drop_caches`. Free jumps up, but now the next requests hit a cold cache: disk read IOPS spike and latency rises for minutes. The alert was wrong, and the "fix" caused the incident.

The correct change was to alert on `MemAvailable` (for example `node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes` in Prometheus node_exporter), and to watch for *symptoms* of real pressure: swap-in/out rates, major page faults, and `oom_kill` events, not the free column.

## The gotcha
**Not everything in `buff/cache` is reclaimable.** `Shmem` (tmpfs such as `/dev/shm` and often `/tmp`, plus SysV/POSIX shared memory) is counted as "Cached" in `/proc/meminfo`, but those pages have no disk file to fall back to. They are only freed by deleting the files, or pushed to swap if you have it. A job that writes 8 GiB into a tmpfs scratch directory makes `buff/cache` look "healthy", yet that memory is effectively gone. `MemAvailable` does subtract it, which is why it is the better metric, but a naive `free + buff/cache` calculation will not.

A second trap: in containers, `free` and `/proc/meminfo` generally show the *host's* numbers (unless a tool like LXCFS virtualizes them), while the cgroup limit is what actually triggers OOM kills. Page cache also counts toward a cgroup's memory usage; it is reclaimed under the limit, but a metric like "container memory usage" that includes cache can look alarming for the same reason as above.

## Try it
Watch cache grow without hurting `MemAvailable` (needs ~1 GiB spare disk and RAM, throwaway container is fine):

```bash
show() { grep -E '^(MemFree|MemAvailable|Cached|Shmem):' /proc/meminfo; echo; }
show
dd if=/dev/zero of=/tmp/pc.bin bs=1M count=1024 status=none; sync
show            # Cached +~1 GiB, MemFree -~1 GiB, MemAvailable ~unchanged
rm /tmp/pc.bin
show            # deleting the file frees its cache instantly

dd if=/dev/zero of=/dev/shm/s.bin bs=1M count=512 status=none
show            # Cached AND Shmem up ~512 MiB, MemAvailable drops ~512 MiB
rm /dev/shm/s.bin
```

On a test run (kernel 6.18), writing a 1 GiB file raised `Cached` by ~1 GiB and left `MemAvailable` within ~25 MiB of where it started. The 512 MiB tmpfs write lowered `MemAvailable` by ~530 MiB. Your numbers will vary, but the pattern should match.

## Think about it
Two nodes both show 10 GiB in `buff/cache` and 1 GiB `free`. On node A, `available` is 11 GiB, and on node B it is 2 GiB. What could the 10 GiB consist of on each node, and what would you read in `/proc/meminfo` to prove it?
