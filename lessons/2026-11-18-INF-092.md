# Terraform state: purpose and resource mapping

`INF-092` · Terraform and infrastructure as code › State and lifecycle · Difficulty 1/3 · ~6 min

> **Why this matters:** Most "Terraform wanted to destroy my database" incidents are really state incidents: the link between code and real infrastructure was lost, stale, or pointed at the wrong thing. Understanding what state *is* explains nearly every confusing plan.

## The moving parts
- **Configuration**: your `.tf` files. They declare resources by *address*, such as `aws_instance.web` or `module.vpc.aws_subnet.private["a"]`. An address is a name in your code, not something the cloud knows about.
- **Remote object**: the real thing in the provider, identified by a provider-assigned ID (for AWS an instance ID like `i-0abc...`).
- **State**: a JSON document (by default `terraform.tfstate`) that records, per resource address, the remote object's ID and the attributes Terraform last saw. It also stores provider and schema metadata and the state serial and lineage.
- **Backend**: where state is stored (local file, S3, etc.). It determines sharing and locking, not the mapping logic.
- **Provider**: the plugin that translates between Terraform's resource model and the provider API (read, create, update, delete).

## How it works
Cloud APIs don't know about your code, and your code doesn't contain cloud IDs. State is the bridge:

```
 config address            state                    real world
 aws_instance.web  ──►  id = i-0abc123   ──►  EC2 instance i-0abc123
 (what you wrote)       attrs = {...}         (what actually exists)
```

The causal chain of `terraform plan`:

1. Terraform loads the configuration and builds a desired graph keyed by address.
2. It loads state. Each address present in state has a remote ID.
3. By default the plan first *refreshes*: it asks the provider to read each tracked object by its ID and updates the in-memory view of its attributes. (`-refresh=false` skips this.)
4. It diffs desired config against refreshed state, per address.
5. The diff yields the action:
   - address in config, **not** in state → **create** (Terraform has no ID, so it assumes nothing exists)
   - address in both, attributes differ → **update** or **replace**
   - address in state, **not** in config → **destroy**
6. On apply, the provider performs the actions, and Terraform writes the new IDs and attributes back to state.

The key consequence of step 5: Terraform decides create vs. destroy from *state membership*, not from looking at the cloud. It will not discover an existing instance by name or tags unless you tell it about the ID (via import).

State also does other jobs: it stores dependency metadata so deletions happen in the right order after you've removed a resource from code, and it caches attribute values, which can make large plans faster. But the mapping is the essential job.

## In production
A team refactors a flat config into modules. `aws_db_instance.main` becomes `module.db.aws_db_instance.main`. Nobody touches the database in AWS. They run `terraform plan` and see:

```
  # aws_db_instance.main will be destroyed
  # (because aws_db_instance.main is not in configuration)
  # module.db.aws_db_instance.main will be created

Plan: 1 to add, 0 to change, 1 to destroy.
```

Cause: the cloud object didn't change, but its *address* did. State still maps `aws_db_instance.main` to the old DB ID, and nothing maps the new address. Per step 5, the old address becomes a destroy and the new one a create. If someone approves that, a production database is deleted (subject to `deletion_protection` or the final-snapshot settings).

Fix: tell Terraform the address moved, so state is rewritten instead of resources recreated. Either a declarative `moved` block in config (Terraform ≥ 1.1):

```hcl
moved {
  from = aws_db_instance.main
  to   = module.db.aws_db_instance.main
}
```

or the imperative `terraform state mv aws_db_instance.main module.db.aws_db_instance.main`. After either, the plan should show no changes.

## The gotcha
State is not a cache you can safely delete. Experienced people treat it like one ("just rerun plan, it'll rebuild"). If state is lost, Terraform has no IDs, so it plans to **create everything again**. That produces duplicate resources, or errors on names that must be unique, while the originals keep running and costing money. Terraform cannot rebuild the mapping from the cloud on its own. You must `terraform import` each object (or use `import` blocks, Terraform ≥ 1.5), and that needs each ID.

A related trap: state can contain secrets in plaintext (database passwords, generated keys), even if the config marks them `sensitive`, since that only redacts CLI output. Treat the state file and its backend as secret material and restrict access.

## Try it
Needs only Terraform (or OpenTofu) and the `local` provider; it touches only a file in a temp directory.

```bash
mkdir /tmp/tfdemo && cd /tmp/tfdemo
cat > main.tf <<'EOF'
resource "local_file" "greeting" {
  content  = "hello"
  filename = "${path.module}/hello.txt"
}
EOF
terraform init && terraform apply -auto-approve
terraform state list            # shows: local_file.greeting
terraform state show local_file.greeting   # the ID and attributes it recorded

# Rename the address in code, no moved block:
sed -i 's/"greeting"/"renamed"/' main.tf
terraform plan                  # look for: 1 to add, 1 to destroy

# Now declare the move instead:
cat >> main.tf <<'EOF'
moved {
  from = local_file.greeting
  to   = local_file.renamed
}
EOF
terraform plan                  # look for: no changes, the resource "has moved"
```

What to look for: the first plan wants to destroy and create (the address changed); the second shows the address move and no infrastructure change.

## Think about it
You delete `terraform.tfstate`, then run `terraform plan` against an unchanged config whose resources all still exist in the cloud. Walk through steps 2 to 5 and predict what the plan says for a resource with a unique-name constraint, such as an S3 bucket. What exactly is missing that would make Terraform plan "no changes" instead, and what are two different ways to supply it?
