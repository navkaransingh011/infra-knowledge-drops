# Feature flags as migration and rollback controls

`INF-195` · CI/CD and deployment engineering › Git and release operations · Difficulty 2/3 · ~6 min

> **Why this matters:** A flag lets you turn a risky behavior off in seconds without redeploying. But flags have their own failure modes: a bad default, a flag store outage, or a flag nobody removed can cause the very outage you were trying to avoid.

## The moving parts
- **Feature flag (toggle):** a runtime conditional in code (`if flag("x"): new() else: old()`) whose value is decided outside the code, by config, a database, or a flag service.
- **Flag provider / store:** where flag values live (a config file, a key-value store, or a hosted service). The app reads it at startup, on a poll, or via streaming updates.
- **Default value:** what the code uses when the provider cannot answer (flag missing, store unreachable, parse error). It is hardcoded at the call site.
- **Evaluation context:** attributes (user ID, tenant, region, host) the flag rules use to decide per request, which enables percentage rollouts.
- **Flag categories** (as classified in Martin Fowler's feature-toggle write-up): *release* toggles (short-lived, hide unfinished work), *ops* toggles (kill switches, can be long-lived), *experiment* toggles (A/B), and *permission* toggles (entitlements). Different lifetimes mean different cleanup rules.

## How it works
A flag decouples **deploy** (code reaches servers) from **release** (behavior reaches users). For a migration, that gives you a safe sequence:

```
deploy code with both paths, flag OFF   -> nothing changes
dual-write to old + new schema          -> new data path warms up
flag ON for 1% -> 10% -> 100% (reads)   -> compare results, watch errors
rollback = flip flag OFF                -> seconds, no deploy
cleanup: delete flag + old path         -> the step people skip
```

The causal chain for safety:
1. Because both code paths ship together, the old path remains a **known-good fallback** that is already deployed.
2. Because the flag is evaluated at runtime, rollback is a config change, not a build and rollout.
3. Because evaluation can use context, you limit the blast radius to a small slice of traffic first.
4. Because the flag provider is itself a dependency, the **default value** decides behavior when it fails. Choose it as the *safe* behavior (usually the old path), not the "intended" one.
5. Because a flag doubles the code paths, the flag is **debt** until the dead branch is removed.

Compatibility is the part flags do *not* solve. Flipping reads back to the old path only works if the old path can still read what the new path wrote. This is the expand/contract rule: keep writes compatible with both versions until the flag is permanently at 100%.

## In production
Setup: a service migrates order totals from a `price` column to a `price_minor` column. Reads are behind `read_price_minor`; writes go to both columns.

What happened: at 25% rollout, error rate on the checkout endpoint climbed and logs showed `NULL value in column price_minor`. An engineer flipped the flag off and reads recovered within the provider's poll interval. But the errors continued for a subset of orders: a second code path, a batch job, wrote only to `price_minor` because it had been updated on a branch that skipped the dual-write.

Why: the flag controlled *reads*, but one writer ignored the compatibility rule, so the "old path" no longer had complete data. The rollback restored the read path but not the data.

Fix: backfill `price` from `price_minor`, put the batch job behind the same dual-write helper, and add a check comparing both columns before raising the rollout percentage again.

## The gotcha
**The default value is part of your rollback plan, and it's usually untested.** When the flag service is down, or a flag is renamed or deleted, the call site falls back to its hardcoded default. Many teams set the default to the *new* behavior ("it's the future") so removing the flag later is trivial. Then a flag-store outage or a typo in the flag key silently activates the new path for 100% of traffic, bypassing your staged rollout. Also, with two services using the same flag, they can fall back at different times and disagree on behavior mid-request.

Test the failure path deliberately: run with the provider unreachable and confirm the system lands on the safe behavior.

## Try it
A minimal local demo of default-on-failure behavior:

```python
flags = {"new_schema_read": {"on": False}}

def flag(name, default):
    try:
        return flags[name]["on"]
    except Exception:
        return default

print(flag("new_schema_read", False))  # configured value: False
print(flag("missing_flag", True))      # key missing -> default used: True
```

Look for the second line: a missing key returns the hardcoded default, not an error. Change the default to `False` and note how a typo in a flag name now fails safe instead of turning the feature on.

## Think about it
Your flag is at 100% for reads, and dual-write has been running for two weeks. You now remove the old read path and the flag in one deploy, but a rolling deployment means old and new instances run side by side for a few minutes. Which instances are still evaluating the flag, what do they do if the provider no longer knows the flag, and what order of steps (flag removal, code removal, old-column writes) avoids a window where one version's behavior is wrong?
