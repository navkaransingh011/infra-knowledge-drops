# Process lifecycle, PID and PPID

`INF-001` · Linux and operating systems › Processes and signals · Difficulty 1/3 · ~6 min

> **Why this matters:** Every "why is there a defunct process?", "who owns this orphan?" and "why didn't my container stop cleanly?" question comes back to how processes are born, identified and reaped. If you can read the PID/PPID columns of `ps`, you can answer most of them.

## The moving parts
- **PID**: the integer the kernel assigns to each process (strictly, each thread group). It is unique among live processes in a PID namespace. The kernel can reuse it after the process is fully gone.
- **PPID**: the PID of the parent, the process that created this one. It is what builds the process tree.
- **`fork()` / `clone()`**: the system call that duplicates the calling process. The child gets a new PID and a copy of the parent's state.
- **`execve()`**: replaces the current process image with a new program. The PID does not change.
- **`wait()` / `waitpid()`**: how a parent collects a child's exit status.
- **Process table entry**: the small kernel record holding a PID and exit status. It is what stays behind after a process exits, until someone waits on it.
- **PID 1 (init)**: the first process in a PID namespace. It adopts orphans.

## How it works
1. A shell wants to run `ls`. It calls `fork()`. The kernel creates a child with a fresh PID, and the child's PPID is the shell's PID.
2. The child calls `execve("/bin/ls", ...)`. Same PID, same PPID, new program.
3. `ls` finishes and calls `exit(status)`. The kernel frees its memory and open files, but **keeps the process table entry** holding the exit status. The process is now a **zombie** (state `Z`, shown as `<defunct>`).
4. The kernel sends the parent `SIGCHLD`. The parent is expected to call `wait()`. That returns the status and **only then** frees the entry and releases the PID.
5. If the parent dies first, its children are **orphaned**. The kernel reparents them, so their PPID changes, to PID 1 of that PID namespace. A nearer ancestor that has set itself up as a "subreaper" (`prctl(PR_SET_CHILD_SUBREAPER)`) takes them instead. The adopter's job is to `wait()` on them when they exit.

```
shell(100) --fork--> child(200) --exec--> ls
                       |  exit(0)
                       v
                  zombie(200)  <-- stays until shell calls wait()
                       |  wait()
                       v
                  PID 200 freed
```

A zombie uses no CPU or memory beyond the table entry. The real cost is the PID it holds. You can't `kill` a zombie, because it is already dead. The fix is to make its parent call `wait()`, or to kill the parent so PID 1 reaps the zombie.

## In production
A service forks a short-lived helper for each request, for example to shell out to an image converter. After a few days on a busy host you see:

```
$ ps -eo pid,ppid,stat,cmd | awk '$3 ~ /Z/' | head -3
 8812  4100 Z    [convert] <defunct>
 8813  4100 Z    [convert] <defunct>
 8814  4100 Z    [convert] <defunct>
$ ps -eo stat | grep -c Z
31842
```

Eventually `fork` fails with `EAGAIN` ("Resource temporarily unavailable"), because the host hit `kernel.pid_max` or a pids cgroup limit. Parent 4100 never calls `wait()`. Its SIGCHLD handling is missing or broken, so every finished helper is stuck as a zombie. `kill -9` on the zombies does nothing. The fix is in the code: reap children with `waitpid(-1, WNOHANG)` in a SIGCHLD handler, or use a library that does it, such as `subprocess.run`. Restarting the parent is the stopgap: the zombies are reparented to PID 1, which reaps them.

## The gotcha
In a container, your application is often PID 1, and many applications don't behave like an init. PID 1 is special in two ways:
- It adopts every orphan in the namespace, but it only reaps them if the code calls `wait()`. An app that spawns grandchildren and never waits on adopted ones leaks zombies. This is the usual case for a shell script or Node/Python app run as PID 1.
- The kernel does not apply default signal actions to PID 1. A signal with no handler installed is ignored, with some exceptions such as `SIGKILL` from outside the namespace. So `docker stop`'s `SIGTERM` can do nothing, and the container only dies after the grace period (10 seconds by default in Docker), when `SIGKILL` arrives.

Fixes: run a tiny init as PID 1 (`docker run --init`, or `tini`), or have the app install handlers and reap.

## Try it
```bash
# PID/PPID of your own shell and a child
echo "shell=$$"; sh -c 'echo "child=$$ parent=$PPID"'

# Make a zombie: the parent exits the child but never waits
python3 - <<'EOF'
import os, time, subprocess
pid = os.fork()
if pid == 0:
    os._exit(0)
time.sleep(0.2)
print(subprocess.run(["ps","-o","pid,ppid,stat,cmd","-p",str(pid)],
      capture_output=True, text=True).stdout)
os.waitpid(pid, 0)   # reap it; now it is gone
EOF

# Make an orphan and watch it be reparented
bash -c 'sleep 30 & echo $!' > /tmp/kid; sleep 0.3
ps -o pid,ppid,cmd -p "$(cat /tmp/kid)"
```
Look for `Z` / `<defunct>` in the first `ps` output. In the second, the sleep's PPID is 1 (or a subreaper's PID), not the exited `bash`. I ran these in a Linux sandbox and saw exactly that. The sleep is harmless and exits after 30 seconds.

## Think about it
A parent process spawns a child and then blocks forever in `sleep()`, ignoring `SIGCHLD`'s effect. The child exits. Trace what the kernel keeps, what it frees, and what you would see in `ps` over time. Then explain why killing the *parent* makes the zombie disappear even though no one ever called `wait()` on it in the original parent.
