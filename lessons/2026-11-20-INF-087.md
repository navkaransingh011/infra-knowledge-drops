# Encryption at rest vs in transit

`INF-087` · Security and identity › Transport and infrastructure security · Difficulty 1/3 · ~6 min

> **Why this matters:** "Everything is encrypted" is the most common and least informative sentence in a security review. Encryption at rest and in transit defend against different attackers, and neither stops someone who holds legitimate credentials.

## The moving parts
- **Data in transit:** bytes moving between two endpoints over a network. It is protected by a protocol such as TLS (HTTPS, database TLS) or IPsec/WireGuard tunnels.
- **Data at rest:** bytes sitting on a medium: disk, volume, snapshot, backup, object store. It is protected by encrypting the storage layer or the data itself.
- **Key:** the secret that lets a party encrypt or decrypt. Where the key lives, and who may use it, decides what the encryption actually defends against.
- **Envelope encryption:** a per-object *data key* encrypts the data, and a *master key* (in a KMS or HSM) encrypts the data key. Storing the wrapped data key next to the data lets you rotate or revoke the master key without re-encrypting everything.
- **Transparent decryption:** most at-rest encryption is applied by the storage layer, which decrypts automatically for any caller the system already authorizes.

## How it works
Each mode protects one segment of the data's journey:

```
client ==TLS==> load balancer ==TLS?==> app ==TLS?==> database --disk encryption--> [disk, snapshot, backup]
       in transit        in transit        in transit              at rest
```

1. **In transit:** the two ends run a handshake, authenticate (usually the server via a certificate) and derive session keys. Records are then encrypted *and* integrity-protected. A passive sniffer sees ciphertext, and an active attacker can't alter bytes without detection. The protection ends when the connection terminates at a TLS endpoint, and from there the data is plaintext in that process's memory.
2. **At rest:** the storage layer encrypts blocks or objects before they hit the medium. Someone who steals a disk, a snapshot or a backup tape gets ciphertext without the key.
3. **Where they meet:** to use data, a server must hold it in plaintext in RAM. At rest protection therefore ends when the storage layer hands data to an authorized reader, and in-transit protection ends at the TLS terminator. Each mode covers only *its own* segment, and the gaps between segments are plaintext.

The attacker model is what separates them:

| Threat | In transit helps? | At rest helps? |
|---|---|---|
| Packet sniffing on the network path | Yes | No |
| Stolen disk / leaked snapshot / discarded hardware | No | Yes |
| Stolen application credentials | No | No (storage decrypts for them) |
| Malicious or compromised host OS with the volume mounted | No | No |

## In production
A team stores customer exports in an object store with server-side encryption enabled, and passes an audit. Months later a support tool's access token leaks. An attacker lists the bucket and downloads thousands of files over HTTPS. The audit logs show ordinary `GetObject`-style reads from an unfamiliar IP, with every request succeeding.

Why it worked: server-side encryption protects the medium, so the service decrypts for any authenticated, authorized request. The token *was* authorized. TLS protected the download from sniffers but delivered it happily to the attacker.

The fix lives elsewhere: least-privilege policies, short-lived credentials, access alerts on unusual read volume, and for the most sensitive data, key policies (for example KMS key permissions) so that bucket access alone is not enough to read the data. Encryption at rest then becomes a second gate, not a decoration.

## The gotcha
"Encrypted in transit" often stops at the edge. TLS terminated at a load balancer, then plaintext HTTP to the backend on a private network, is a common design. It is legitimate only if you have decided that the internal network is trusted. Anyone who can sniff or tap that segment (a compromised node, a mirrored port, a sidecar with broad network access) reads everything. Likewise, "disk encryption" on a VM protects against stolen hardware, not against a root shell on the running machine, because the volume is already unlocked there. Ask "encrypted *against whom*, between *which two points*?" every time.

## Try it
Encryption at rest, in miniature (OpenSSL 3.x, throwaway directory):

```bash
cd "$(mktemp -d)"
echo "card=4111" > secret.txt
openssl enc -aes-256-cbc -pbkdf2 -pass pass:demo -in secret.txt -out secret.enc
grep -c 4111 secret.enc            # 0: plaintext not found in the stored bytes
openssl enc -d -aes-256-cbc -pbkdf2 -pass pass:demo -in secret.enc   # anyone with the key reads it
```

Encryption in transit, from a client's view:

```bash
openssl s_client -connect example.com:443 -brief </dev/null
```

Look for the negotiated protocol (for example `TLSv1.3`) and the verification result. Then compare with `curl -v http://example.com` to see an unencrypted exchange.

## Think about it
A service terminates TLS at a load balancer, talks plaintext to an app, and the app reads from a database on an encrypted volume. List every point where the data exists as plaintext, and for each one name who (or what) could read it. Which single change would shrink that list the most, and what does it still leave exposed?
