# Container PID 1 and graceful shutdown

`INF-112` · Docker and containers › Container fundamentals · Difficulty 3/3 · ~6 min

> **Why this matters:** Every deploy, scale-down and node drain ends with someone sending SIGTERM to your container. If the process that should handle it never sees it, you get a silent 10–30 second stall followed by SIGKILL: dropped requests, unflushed buffers, half-finished jobs.

## The moving parts
- **PID namespace:** a kernel feature giving a container its own process-ID numbering. The first process started inside it is PID 1.
- **PID 1 (init):** in a PID namespace, the process whose death tears the whole namespace down. The kernel treats it specially for signals (below).
- **Shell form vs exec form:** in a Dockerfile, `CMD myapp --flag` (shell form) runs `/bin/sh -c "myapp --flag"`; `CMD ["myapp","--flag"]` (exec form) runs `myapp` directly.
- **Stop sequence:** `docker stop` sends the stop signal (SIGTERM by default, changeable with `STOPSIGNAL` or `--stop-signal`) to PID 1 of the container, waits a grace period (10 s by default, `-t`/`--time` to change), then sends SIGKILL. Kubernetes does the same with `terminationGracePeriodSeconds` (default 30 s).

## How it works
1. The runtime starts the container's entrypoint as PID 1 of a new PID namespace.
2. `docker stop` sends SIGTERM **only to that one process**, not to the whole process tree.
3. For PID 1, the kernel delivers a signal from outside the namespace only if PID 1 has installed a handler for it. A normal process with no handler would die from SIGTERM; PID 1 instead ignores it. (SIGKILL and SIGSTOP from an ancestor namespace are always forced through, which is why the final SIGKILL works.)
4. With shell form, PID 1 is `sh`, and your app is its child. `sh` has no SIGTERM handler that forwards to children, so the signal is dropped, and your app never learns it should stop.
5. The grace period expires, SIGKILL kills `sh`, and with PID 1 gone the kernel kills every other process in the namespace.

```
docker stop ──SIGTERM──▶ PID 1: sh -c "myapp"   (no handler → ignored)
                            └── PID 7: myapp    (never signalled)
        ...10s...  ──SIGKILL─▶ PID 1 dies → namespace torn down → myapp killed
```

Fixes, in order of preference:
- **Exec form:** `ENTRYPOINT ["myapp"]` makes your app PID 1. It must install its own SIGTERM handler, because PID 1 gets no default action.
- **`exec` in wrapper scripts:** end an entrypoint script with `exec myapp "$@"` so the shell is replaced rather than left as parent.
- **A tiny init:** `docker run --init` (or `init: true` in Compose) puts a small init (tini) at PID 1; it forwards signals and reaps zombies.

## In production
A team ran an API as `CMD gunicorn app:app` inside a Kubernetes pod with a 30 s grace period. During rollouts, clients saw 502s and the pod's termination always took *exactly* 30 s. Logs showed no "shutting down" line from the app on SIGTERM, and `kubectl get pod` sat in `Terminating` for the full period. Cause: shell-form CMD left `sh` as PID 1; SIGTERM never reached gunicorn, so in-flight requests were cut off by SIGKILL. Fix: exec form `CMD ["gunicorn","app:app"]`. Terminations dropped to the time gunicorn actually needs to drain. The tell-tale is a stop time that equals the grace period to the second.

## The gotcha
"My shell will just exec the last command, right?" Not reliably. Some shells optimize `sh -c 'cmd'` into an exec, others don't. In my test on Debian/Ubuntu-style `dash`, `sh -c 'sleep 30'` still left `sh` as the parent of `sleep`. And a wrapper script that does setup work then runs `myapp` without `exec` has the same problem. Likewise, even with exec form, if your app is PID 1 and has no SIGTERM handler, SIGTERM is ignored. Runtimes whose default handling "just works" outside a container (e.g. a bare Python script, which dies on SIGTERM) will hang as PID 1 until you register a handler.

## Try it
Requires root and `unshare` (util-linux); no Docker needed.
```bash
# Shell as PID 1; the signal is sent from the host (outside the namespace)
sudo unshare --pid --fork --mount-proc sh -c 'sleep 300; echo done' &
sleep 1
ps -eo pid,ppid,cmd | grep -E 'sh -c sleep|sleep 300' | grep -v grep   # note sh is parent of sleep
SH=$(pgrep -f "sh -c sleep 300; echo done" | head -1)
sudo kill -TERM $SH; sleep 1; ps -p $SH      # still alive: SIGTERM ignored
sudo kill -KILL $SH                          # SIGKILL works
```
With Docker, compare `docker run --rm -d --name t alpine sh -c 'sleep 300; echo x'` with the `--init` variant and `time docker stop t`: the first takes about 10 s, the second returns immediately. (Alpine's busybox `sh` may exec a single trailing command, so use a two-command string as above.)

## Think about it
Your entrypoint script runs `trap 'kill $CHILD' TERM; myapp & CHILD=$!; wait`. `docker stop` now stops quickly, but the exit code is 143 and zombies pile up when `myapp` spawns short-lived helpers. Using what you know about who reaps orphans in a PID namespace, why does that happen, and what does `--init` change?
