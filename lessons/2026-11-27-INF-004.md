# PID 1 and signal handling in containers

`INF-004` · Linux and operating systems › Processes and signals · Difficulty 3/3 · ~6 min

> **Why this matters:** Pods that take exactly 30 seconds to terminate, `docker stop` that always hangs 10 seconds, and in-flight requests dropped on every deploy are often the same bug. Your app is PID 1, and the kernel treats PID 1 specially.

## The moving parts
- **PID namespace:** a kernel feature giving a container its own process-ID numbering. The first process started inside it gets PID 1.
- **PID 1 ("init"):** on a normal host, init reaps orphaned children and has no default signal behavior of its own. Inside a PID namespace the kernel gives the namespace's PID 1 the same protections.
- **SIGTERM vs SIGKILL:** SIGTERM is a polite request that a process may handle or ignore. SIGKILL cannot be caught or ignored (prerequisite topic).
- **Container runtime stop:** `docker stop` sends SIGTERM to the container's PID 1, waits a grace period (default 10 s), then sends SIGKILL. Kubernetes does the same with `terminationGracePeriodSeconds` (default 30 s).

## How it works
Normally, if a process has installed no handler for SIGTERM, the kernel applies the *default action*: terminate. PID 1 of a PID namespace is the exception. The kernel only delivers a signal to it if PID 1 has explicitly installed a handler. Signals with default dispositions are discarded, and that includes SIGTERM and SIGINT. Signals sent from *inside* the namespace, even SIGKILL, are ignored this way. SIGKILL and SIGSTOP sent from an *ancestor* namespace (the host, or the runtime) are still forced through.

The causal chain for a "stuck" stop:

```
docker stop / kubelet
   │  SIGTERM → container PID 1
   ▼
PID 1 has no SIGTERM handler  → kernel discards the signal
   ▼
app keeps running, nothing drains, nothing closes
   ▼
grace period expires (10s docker / 30s k8s by default)
   ▼
SIGKILL from the parent namespace → forced, instant death, no cleanup
```

A second PID 1 duty makes it worse: **zombie reaping.** When a process's parent dies, its children are reparented to PID 1. If your app as PID 1 never calls `wait()`, exited orphans stay as zombies and hold process-table entries.

## In production
A team ships a Python API with `CMD ["sh", "-c", "gunicorn app:app"]` on Kubernetes. Every rollout, old pods sit in `Terminating` for the full 30 s and clients see connection resets. Symptoms: the pod's last log line is minutes old, with no "shutting down" message. Duration is always ≈ `terminationGracePeriodSeconds`, which points to SIGKILL. Cause: `sh` is PID 1. It received SIGTERM and, having no handler, ignored it. Gunicorn (a child) never heard it. Fix, in order of preference:

1. Use `exec gunicorn ...` (or the JSON-form `CMD ["gunicorn", "app:app"]`) so the app *is* PID 1, and make sure it handles SIGTERM. Gunicorn does, but a naive script may not.
2. Or run a tiny init as PID 1 that forwards signals and reaps zombies: `docker run --init` (uses tini), or `tini`/`dumb-init` as ENTRYPOINT.

## The gotcha
Handling SIGTERM isn't enough if the shell wrapper stays between the runtime and your app. `CMD gunicorn app:app` (shell form) becomes `/bin/sh -c "gunicorn app:app"`. Some shells exec the last command, and some (or any script with more than one command) do not. The behavior depends on the shell and script, so "it worked in testing" is not proof. Related trap: signals sent from inside the container to PID 1 are dropped, so `kill -TERM 1` from `docker exec` can appear to do nothing for a handler-less process, which tempts people into misdiagnosing the app. And because it only ignores signals *without handlers*, a PID 1 that does install a handler (Python code below) behaves normally. The special case is specifically about the missing handler.

## Try it
Needs Linux and root (or a throwaway container). `unshare` makes a PID namespace without Docker.

```bash
cat > /tmp/p1.py <<'EOF'
import os, signal, time
print("pid", os.getpid(), flush=True)
if os.environ.get("H"):
    signal.signal(signal.SIGTERM, lambda s, f: (print("got TERM", flush=True), os._exit(0)))
time.sleep(30)
EOF
# no handler: run, then from another shell `kill -TERM <host pid>` (find via pgrep -f p1.py)
unshare --pid --fork python3 /tmp/p1.py
# with handler
H=1 unshare --pid --fork python3 /tmp/p1.py
```

Both print `pid 1`. Without the handler, SIGTERM from the host does nothing, and `kill -KILL` from the host ends it. With the handler, it prints `got TERM` and exits. (I observed exactly this on Linux 6.18; the unshare run may print a harmless `sigprocmask` warning.) With Docker: compare `docker run --rm -d --name t alpine sleep 300; time docker stop t` (about 10 s, since busybox `sleep` as PID 1 has no handler) with the same command plus `--init` (returns almost immediately).

## Think about it
`kill -TERM 1` run *inside* a container whose PID 1 is `sleep` does nothing, yet `docker stop` still kills it after 10 s. Both are signals aimed at the same process. What differs about the sender, and what does that tell you about which kernel check applies? Then: what would change if the container shared the host's PID namespace?
