# Readiness vs liveness vs startup probes

`INF-130` · Kubernetes › Probes and traffic · Difficulty 2/3 · ~6 min

> **Why this matters:** A wrong probe turns a slow boot or a slow dependency into an outage. A too-eager liveness probe restarts healthy-but-busy pods in a loop. A missing readiness probe sends traffic to pods that can't serve it yet.

## The moving parts
- **kubelet**: the node agent. It runs the probes and acts on the results. Probes are not run by the control plane.
- **Readiness probe**: asks "should this pod receive traffic right now?" On failure the pod is marked NotReady and removed from Service endpoints. The container is *not* restarted.
- **Liveness probe**: asks "is this container stuck beyond recovery?" On failure the kubelet kills the container and restarts it according to `restartPolicy`.
- **Startup probe**: asks "has the app finished booting?" While it hasn't succeeded, the kubelet holds off the liveness and readiness probes. It is stable since Kubernetes 1.20.
- **Probe knobs**: `initialDelaySeconds`, `periodSeconds`, `timeoutSeconds`, `failureThreshold`, `successThreshold`. Check the defaults for your version in the docs. As I recall, they are 10s period, 1s timeout, 3 failures and 1 success.

## How it works
Each container can have all three probes, and each has a different consequence:

```
container starts
   │
   ▼
startupProbe ──fail x N──► container killed, restarted
   │ success (once)
   ▼
 ┌─────────────────────────────┐
 │ livenessProbe  ──fail──► restart container
 │ readinessProbe ──fail──► remove pod from endpoints
 └─────────────────────────────┘
```

1. The container starts and the app begins loading (caches, migrations, JIT warmup).
2. If a startup probe exists, the kubelet runs only that probe. The app gets up to `failureThreshold × periodSeconds` to pass it.
3. Once the startup probe succeeds, it never runs again. Liveness and readiness take over on their own schedules.
4. Readiness decides who sends traffic to the pod. Liveness decides whether the process gets killed.

The key design point is that liveness and readiness have different consequences. Readiness failure sheds load and is reversible. Liveness failure destroys state and is disruptive.

Without a startup probe, the only way to protect a slow booter from liveness is a large `initialDelaySeconds`. That delay is also paid on every healthy restart, so it slows recovery.

## In production
A Java service takes about 90s to warm up. Its liveness probe was `httpGet /health` with `periodSeconds: 10` and `failureThreshold: 3`, so it had about 30s to start.

- **Symptom:** `kubectl get pods` shows `CrashLoopBackOff` with a climbing restart count. The service never becomes available.
- **Evidence:** `kubectl describe pod` shows events like `Liveness probe failed: Get "http://10.0.1.5:8080/health": connection refused`, followed by `Container app failed liveness probe, will be restarted`. The exit reason looks like a SIGTERM kill, not an application crash.
- **Cause:** the liveness probe started before the app finished booting. Each restart reset the clock and the app never got its 90s.
- **Fix:** add a startup probe that allows the full boot, for example `failureThreshold: 30` and `periodSeconds: 5` for up to 150s. Keep liveness tight afterwards.

## The gotcha
**Don't make liveness depend on downstream dependencies.** If `/health` checks the database and the database blips, every pod fails liveness at the same moment. They all restart together, reconnect together and hammer the recovering database. You've turned a partial outage into a full one.

Make liveness check only "is this process able to make progress" (for example, the event loop responds). Put dependency checks in readiness, where failure just removes pods from rotation.

Related caveat: readiness also removes *all* pods at once if a shared dependency is down. That is often the right behavior, but be aware that it produces 503s from the Service rather than errors from individual pods.

## Try it
```yaml
# probes.yaml
apiVersion: v1
kind: Pod
metadata:
  name: probe-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 20; touch /tmp/ready; sleep 3600"]
    startupProbe:
      exec: {command: ["cat", "/tmp/ready"]}
      periodSeconds: 2
      failureThreshold: 30
    readinessProbe:
      exec: {command: ["cat", "/tmp/ready"]}
      periodSeconds: 5
    livenessProbe:
      exec: {command: ["cat", "/tmp/ready"]}
      periodSeconds: 5
      failureThreshold: 2
```
```bash
kubectl apply -f probes.yaml   # needs kind/minikube
kubectl get pod probe-demo -w
kubectl describe pod probe-demo | grep -i -A3 probe
```
Look for: the pod stays `0/1 Ready` for about 20s with zero restarts. Now lower `failureThreshold` on the startup probe to 3 and re-apply (delete the pod first). You'll see startup probe failures and restarts.

## Think about it
Say you give a slow-booting app a liveness probe with a 5-minute `initialDelaySeconds` instead of a startup probe. The app then hangs permanently 10s after a *later* restart. Trace what the kubelet does, and how long the pod stays broken, compared with the startup-probe design. What does that tell you about when each probe is evaluated?
