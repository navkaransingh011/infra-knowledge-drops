# At-most-once, at-least-once and effectively-once delivery

`INF-160` · Distributed systems and messaging › Delivery semantics and message processing · Difficulty 2/3 · ~6 min

> **Why this matters:** Every queue or log you run will, at some point, lose a message or deliver one twice, usually during a deploy or a crash. Which of the two you get is decided by one ordering choice in your consumer. Knowing that choice is how you avoid double charges and silently dropped events.

## The moving parts
- **Producer:** sends messages and waits (or not) for an acknowledgement from the broker.
- **Broker:** stores messages durably (a queue or a log) and hands them out.
- **Consumer:** reads a message, does a side effect (DB write, API call), then tells the broker it is done.
- **Ack / offset commit:** the consumer's "I'm finished" signal. In a queue it deletes the message. In a log such as Kafka it advances a stored position.
- **Crash window:** the gap between the side effect and the ack. A process can die inside it, and the network can fail inside it too.

## How it works
Two actors can fail between "do the work" and "record that the work is done". You cannot make both steps atomic across two different systems, so you pick which failure you prefer.

```
at-most-once :  ack/commit --> process      crash between => message LOST
at-least-once:  process    --> ack/commit   crash between => message REDELIVERED (duplicate)
```

1. **At-most-once.** Commit first, then process. If the consumer dies after the commit, the broker believes the message is handled and never sends it again. You get zero or one processing, never two. On the producer side the equivalent is fire-and-forget with no retry.
2. **At-least-once.** Process first, then commit. If the consumer dies before the commit, the broker redelivers. The same applies to the producer: if the ack is lost, the producer retries and the broker may store the message twice. You get one or more processing, never zero.
3. **Exactly-once** across independent systems is not achievable by the broker alone. What you can build is **effectively-once**: at-least-once delivery plus an operation that is safe to repeat, so duplicates have no extra effect. There are two ways to get there:
   - **Idempotent consumer:** record a message ID (or use a natural key) and make the write conditional, for example `INSERT ... ON CONFLICT DO NOTHING`, or an upsert.
   - **Transactional write of effect and position together:** if the output and the consumed offset commit in one transaction, a replay overwrites rather than duplicates. Kafka's transactions do this for Kafka-to-Kafka pipelines (producer `transactional.id`, consumers on `isolation.level=read_committed`). Kafka's idempotent producer, which dedups producer retries within a partition, has been on by default since Kafka 3.0.

AWS SQS shows the same split. Standard queues are at-least-once, so the same message may arrive more than once. FIFO queues dedup on a `MessageDeduplicationId` within a 5-minute window, which removes producer retry duplicates but does not protect a consumer that crashes before deleting the message.

## In production
A payments service consumes `order-paid` events from a queue and calls a partner API to issue a receipt email, then acks. During a rolling deploy, pods get SIGKILLed after the grace period. Customers start reporting two receipts for the same order. The queue dashboard shows a redelivery spike, and the logs show the same `order_id` handled by two different pod names a few seconds apart.

Cause: the handler sent the email (the side effect), then acked. Pods killed between those two lines left the message unacked, so it became visible again and another pod processed it. This is at-least-once working exactly as designed.

Fix: store `order_id` in a `receipts_sent` table with a unique constraint, and check or insert it before sending. Better still, pass the partner API an idempotency key derived from `order_id` if it supports one. The duplicates stay in the queue, but they no longer cause a second email.

## The gotcha
"I use a FIFO or transactional broker, so I have exactly-once" is wrong more often than people expect. Broker-side dedup covers the producer-to-broker hop. The consumer's side effect, such as an HTTP call or a write to a database that is not part of the transaction, is outside that boundary. Kafka's transactional guarantee only holds when the read, the write and the offset commit are all inside Kafka. As soon as your handler touches an external system, you are back to needing an idempotent write.

A second trap: committing offsets on a timer (auto-commit) while processing asynchronously can silently turn at-least-once into at-most-once. The offset advances past messages still in flight, and a crash loses them.

## Try it
This pure-Python simulation (no dependencies) models a consumer that crashes 30% of the time inside the crash window, under each ordering.

```python
import random
def run(order, crash_p=0.3, n=1000, seed=1):
    random.seed(seed)
    offset = 0; processed = []
    while offset < n:
        msg = offset
        if order == "commit-first":              # at-most-once
            offset += 1
            if random.random() >= crash_p: processed.append(msg)
        else:                                      # process-first: at-least-once
            processed.append(msg)
            if random.random() >= crash_p: offset += 1
    lost = n - len(set(processed)); dup = len(processed) - len(set(processed))
    print(f"{order:13} lost={lost:4} duplicates={dup:4}")
run("commit-first"); run("process-first")
```

Look for: `commit-first` shows lost messages and zero duplicates; `process-first` shows zero lost and many duplicates. (With seed 1, I got lost=280 and duplicates=397 respectively.) Now add `processed` as a set keyed by message ID and count side effects. Duplicates vanish, which is effectively-once.

## Think about it
Your consumer does `process → commit offset`, and the process step is an idempotent upsert. A teammate "optimizes" it by batching: process 500 messages, then commit once. Nothing about correctness seems to change, yet recovery after a crash now takes longer and the downstream sees a burst of old data.
