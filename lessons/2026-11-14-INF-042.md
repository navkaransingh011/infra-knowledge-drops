# HTTP request lifecycle and status codes

`INF-042` · Networking and protocols › HTTP, TLS and proxies · Difficulty 1/3 · ~6 min

> **Why this matters:** The first question in almost every incident is "who produced this error?" A 502, a 504 and a 500 point at three different machines, and mixing them up sends you debugging the wrong tier for an hour.

## The moving parts
- **Client**: the browser, `curl` or service making the request. It builds the request and interprets the response.
- **Origin server**: the application that actually owns the resource and decides what the answer is.
- **Gateway / reverse proxy**: a server such as nginx, Envoy or a cloud load balancer that receives the client's request and forwards it to an upstream (the origin or another proxy). RFC 9110 calls an intermediary that acts as the origin for the client a *gateway*. It exists for TLS termination, routing and load balancing.
- **Request**: a start line (`GET /orders/7 HTTP/1.1`), header fields, a blank line, an optional body.
- **Response**: a status line (`HTTP/1.1 200 OK`), header fields, a blank line, an optional body.
- **Status code**: a three-digit number whose first digit gives the class: `1xx` informational, `2xx` success, `3xx` redirection, `4xx` client error, `5xx` server error.

## How it works
One request/response exchange is a causal chain:

```
client ──DNS──► IP ──TCP (+TLS)──► gateway ──(new connection)──► origin
   │                                   │                            │
   │ 1. send request line+headers+body │ 2. pick upstream, forward  │ 3. run app logic
   │◄────────── 6. response ◄──────────┤◄──── 5. response ◄─────────┘ 4. choose status
```

1. The client resolves the name, opens a TCP connection (and does the TLS handshake for `https`), then sends the request. The `Host` header is what lets one IP serve many sites.
2. The gateway parses the request and chooses an upstream. If it cannot connect to the upstream, or the upstream sends garbage, the gateway itself fabricates an error response.
3. The origin runs its logic and picks a status code.
4. The response travels back. The client reads the status line first, and only then decides what to do: follow a redirect, retry, or surface the error.

The status class tells you **whose fault the protocol says it is**:
- **4xx**: the request is wrong as sent, so repeating it unchanged will not help (`400` malformed, `401` unauthenticated, `403` forbidden, `404` not found, `429` too many requests).
- **5xx**: the request may be fine, but the server side failed to complete it.

Within 5xx, three codes matter most for finding the broken tier (RFC 9110 §15.6):
- **500**: the origin hit an unexpected condition, typically an unhandled exception. Look at application logs.
- **502 Bad Gateway**: a gateway got an *invalid response or no usable response* from the upstream. Upstream crashed, refused the connection, or closed it mid-response.
- **504 Gateway Timeout**: a gateway did not get a response from the upstream *in time*. The upstream is up but slow or hung.
- Also useful: **503 Service Unavailable** means the server is temporarily unable to handle the request (overload, maintenance) and may send `Retry-After`.

Rule of thumb: 502 means "upstream answered wrongly or not at all", 504 means "upstream didn't answer before my timeout".

## In production
A checkout service sits behind nginx. After a deploy, users see intermittent errors and the dashboard shows a spike of 502s from the load balancer, with the app's own 5xx counter at zero.

The nginx error log says:

```
connect() failed (111: Connection refused) while connecting to upstream, upstream: "http://10.0.3.12:8080/checkout"
```

The app's logs show nothing, because the requests never reached it. The cause: pods restarting on the new version took a few seconds to start listening, yet were already registered as upstream targets. nginx's connect failed, and nginx returned 502.

Two days later the symptom flips to 504s. nginx logs `upstream timed out (110: Operation timed out) while reading response header from upstream`. This time the app is up, but a slow database query holds requests longer than nginx's `proxy_read_timeout` (60s by default in nginx). The app logs show requests *completing* at 75s, after the client already got a 504.

Fixes: for the 502s, add a readiness check so targets only receive traffic once they listen. For the 504s, fix or time-box the slow query, and only then consider raising the timeout.

## The gotcha
**The code on the wire may not come from the service you think you are debugging.** A 504 does not mean your app crashed; it often means your app is *still working* after the gateway gave up, so the side effect (a payment, a row insert) can still happen. A client that retries on 504 can then double-execute a non-idempotent `POST`.

The related trap is reading 5xx counts only from the app. Gateway-generated 502/504s never reach app metrics, so the app looks healthy while users are failing. Always compare the gateway's status counts with the app's. Also note that a gateway can *forward* an origin's 502 or 504 unchanged when it is itself chained to another gateway, so check which hop's log line says "upstream".

## Try it
```bash
# 1. Serve a directory and watch the exchange
mkdir /tmp/demo && cd /tmp/demo && echo hi > index.html
python3 -m http.server 8099 &
curl -sv http://localhost:8099/index.html 2>&1 | grep -E '^[<>]'
# Look for: the request line, Host header, then "< HTTP/1.0 200 OK" (Python's server replies HTTP/1.0)

# 2. A 4xx from the origin
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8099/nope     # 404

# 3. No server at all: no HTTP status exists
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8098/; echo "exit $?"
# Look for: 000 (curl's placeholder, nothing was received). A gateway would turn this into a 502.

kill %1
```
