# Idle resources and orphaned infrastructure

`INF-245` · Cloud economics › Cost and capacity · Difficulty 1/3 · ~6 min

> **Why this matters:** Cloud bills are driven by what exists, not what is used. Resources that lost their owner (a deleted instance, a finished experiment) keep billing every hour until someone notices, and nothing in the platform will ever tell you.

## The moving parts
- **Orphan:** a resource whose consumer is gone but which itself was not deleted. Example: an EBS volume whose instance was terminated.
- **EBS volume (AWS):** network block storage. It is billed per provisioned GB-month, whether or not it is attached or even written to. An unattached volume has status `available`.
- **EBS snapshot (AWS):** a point-in-time, incremental backup of a volume stored in S3-managed storage. It is billed for the blocks it uniquely holds and outlives the volume it came from.
- **Elastic IP (AWS):** a static public IPv4 address you allocate to your account. It exists independently of any instance.
- **Idle vs orphaned:** idle resources still have an owner but do no work (a 2%-CPU instance). Orphans have no owner at all. Orphans are safer to find; idle resources need a human judgement.

## How it works
Orphans come from a lifecycle mismatch: the parts of a system are created together but deleted separately.

```
create instance ──► attach volume ──► snapshot volume ──► allocate EIP
        │                                   │                  │
terminate instance                          │                  │
        │                                   ▼                  ▼
 volume survives (if DeleteOnTermination=false)   snapshot survives   EIP now idle
        ▼
 status=available, still billed
```

1. Deleting a parent (instance, cluster, stack) only deletes children that were explicitly tied to it. Root volumes are usually flagged `DeleteOnTermination=true` by default. Extra data volumes attached at launch typically default to `false`, so they survive termination (check the flag in your own launch templates).
2. Anything created by a side channel (a manual snapshot, a console-allocated IP, a backup tool) has no link to the parent at all.
3. Billing keys off existence. Since 1 Feb 2024, AWS charges $0.005 per hour per public IPv4 address, in use or not (about $3.65/month), and idle Elastic IPs were already charged before that.
4. So detection is a join: list resources of each type, then find those with no live consumer, and then check age and tags.

## In production
A team ran a load-test sprint with `terraform apply` for 40 instances, each with a 500 GB data volume added by a script (`aws ec2 attach-volume`, outside Terraform) and a nightly snapshot job. After `terraform destroy` the instances vanished. The next month, Cost Explorer showed EBS spend up about $2,000 with no matching instances. Cost Explorer grouped by usage type showed `EBS:VolumeUsage.gp3` and `EBS:SnapshotUsage` still climbing.

Cause: Terraform only knew about the instances, so destroy never touched the volumes created by the script (the attach was outside its state), and the snapshot job kept existing snapshots indefinitely. The fix was a list-then-review sweep (below), tagging every resource with `owner` and `expires` at creation, and a snapshot lifecycle policy with a retention count.

## The gotcha
Deleting the "obvious" orphan often fails or silently does nothing, because **dependencies are hidden in the other direction**. A snapshot that backs a registered AMI cannot be deleted until the AMI is deregistered. A volume that looks unattached may be a restore target for a backup tool, or a recovery copy someone detached on purpose during an incident. And `available` does not mean abandoned: it only means unattached. Bulk-deleting by status alone is how teams destroy the one volume holding the only copy of a database. Always check age, tags, and CloudTrail for the last attach event before deleting, and snapshot first if unsure (a snapshot is far cheaper than a lost volume).

Incremental snapshots add a second wrinkle: deleting one snapshot in a chain frees only the blocks no other snapshot references, so deleting a single old snapshot may reduce your bill by less than you expect.

## Try it
These need an AWS account and credentials; all are read-only (`describe-*`).

```bash
# Unattached volumes: size, age
aws ec2 describe-volumes --filters Name=status,Values=available \
  --query 'Volumes[].[VolumeId,Size,CreateTime,Tags[?Key==`owner`]|[0].Value]' --output table

# Elastic IPs with no association
aws ec2 describe-addresses \
  --query 'Addresses[?AssociationId==null].[PublicIp,AllocationId]' --output table

# Snapshots you own, oldest first
aws ec2 describe-snapshots --owner-ids self \
  --query 'sort_by(Snapshots,&StartTime)[].[SnapshotId,StartTime,VolumeSize,Description]' --output table
```

Look for volumes with `owner` empty and a `CreateTime` months old, and snapshots whose `Description` mentions an instance or AMI that no longer exists. Cross-check snapshot IDs against `aws ec2 describe-images --owners self` before deleting.

## Think about it
Your sweep script deletes every `available` volume older than 30 days, and one day it destroys a volume a team was keeping detached on purpose. Which information was missing at deletion time, and how could the creation-time design (tags, lifecycle links, a grace "quarantine" step) have supplied it without making the sweep slower?
