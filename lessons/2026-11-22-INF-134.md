# Kubernetes DNS and service discovery

`INF-134` · Kubernetes › Probes and traffic · Difficulty 2/3 · ~6 min

> **Why this matters:** Almost every in-cluster call starts with a DNS lookup. When CoreDNS is slow or misconfigured, you see "random" timeouts and 5xx errors across unrelated services, and the cause is easy to miss because the application logs only say `connection timed out`.

## The moving parts

- **CoreDNS**: the cluster DNS server, normally run as a Deployment in `kube-system` and exposed by a Service called `kube-dns`. Its `kubernetes` plugin answers names for Services by watching the API server (Services and EndpointSlices).
- **Corefile**: CoreDNS's config, stored in the `coredns` ConfigMap. It chains plugins: `kubernetes` for `cluster.local`, `forward` for everything else, `cache`, `loop`, and so on.
- **kubelet's resolv.conf injection**: when a pod starts, the kubelet writes the pod's `/etc/resolv.conf`. With the default `dnsPolicy: ClusterFirst`, it points `nameserver` at the `kube-dns` Service IP and adds search domains.
- **Search domains and `ndots`**: the resolver appends each search domain to a name that has fewer than `ndots` dots before trying it as an absolute name. Kubernetes sets `ndots:5`.

## How it works

A typical pod's `/etc/resolv.conf`:

```
search app.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
```

When your app calls `orders` (in namespace `app`), the chain is:

1. `orders` has 0 dots, fewer than 5, so the libc resolver walks the search list first: `orders.app.svc.cluster.local`.
2. The query goes to the `kube-dns` ClusterIP. kube-proxy (or the CNI) load-balances it to a CoreDNS pod.
3. The `kubernetes` plugin finds Service `orders` in namespace `app` and returns its ClusterIP as an A record. If it were a headless Service, it would return the ready pod IPs instead.
4. The client connects to the ClusterIP, and the Service layer picks a backend from the EndpointSlices.

```
app --> resolv.conf --> kube-dns ClusterIP --> CoreDNS pod
                                   |-- *.cluster.local -> kubernetes plugin (API watch)
                                   '-- everything else -> forward -> upstream resolver
```

Now the important consequence. For an external name such as `api.example.com` (2 dots, fewer than 5), the resolver tries `api.example.com.app.svc.cluster.local`, then `...svc.cluster.local`, then `...cluster.local`, and only then the bare name. Each failed attempt is an NXDOMAIN round trip, and clients usually do A and AAAA lookups for each. One external call can therefore cause roughly 8 queries to CoreDNS instead of 2.

Names that are not in `cluster.local` go through the `forward` plugin, which by default uses the node's `/etc/resolv.conf` upstreams.

## In production

A service making many outbound calls to a third-party API starts logging intermittent `dial tcp: lookup api.partner.com: i/o timeout` during a traffic peak. CoreDNS CPU is pinned at its limit and its pods are CPU-throttled. Request count at CoreDNS is several times the application's actual lookup rate, and most of it is NXDOMAIN for names ending in `.svc.cluster.local`.

The cause is search-path amplification plus too few CoreDNS replicas for the load. Fixes, in order of preference:

- Use fully qualified names with a trailing dot (`api.partner.com.`) in hot paths, or set a lower `ndots` (often 2) via `dnsConfig` in the pod spec. Check that no in-cluster short names like `orders.app` stop resolving.
- Scale CoreDNS (or autoscale it) and remove CPU throttling.
- Consider node-local caching (NodeLocal DNSCache), which reduces load and avoids conntrack pressure on UDP DNS.

## The gotcha

The `loop` plugin and the node's resolv.conf. If the node's `/etc/resolv.conf` points at a local stub like `127.0.0.53` (systemd-resolved), the `forward . /etc/resolv.conf` default makes CoreDNS forward queries to itself. CoreDNS's `loop` plugin detects that and deliberately halts the process, so pods go into `CrashLoopBackOff` with a log line like `Loop ... detected`. The fix is to point `forward` at the real upstream resolvers (or the kubelet's `--resolv-conf` at the non-stub file), not to remove `loop`. The trap is that this appears after a node image or OS change, when nothing in Kubernetes itself changed.

A second trap in the same area: a pod with `hostNetwork: true` uses the node's resolver, not CoreDNS, unless you set `dnsPolicy: ClusterFirstWithHostNet`. Such pods cannot resolve Service names.

## Try it

```bash
# Throwaway cluster (kind or minikube), then:
kubectl run dnstest --image=busybox:1.36 --restart=Never -- sleep 3600
kubectl exec dnstest -- cat /etc/resolv.conf
kubectl exec dnstest -- nslookup kubernetes.default
kubectl exec dnstest -- nslookup kubernetes.default.svc.cluster.local.
kubectl -n kube-system get cm coredns -o yaml     # read the Corefile
kubectl -n kube-system logs deploy/coredns
kubectl delete pod dnstest
```

Look for `ndots:5` and the three search domains in `resolv.conf`, and the `kubernetes`, `forward`, `cache` and `loop` entries in the Corefile.
