# Software supply-chain signing and provenance

`INF-090` · Security and identity › Transport and infrastructure security · Difficulty 3/3 · ~7 min

> **Why this matters:** A registry tag is a mutable pointer, and anyone with push access can repoint it. Signing and provenance let a cluster ask "did my CI build this exact digest, from this repo?" instead of "does it have a familiar name?"

## The moving parts
- **Digest**: the `sha256:...` hash of an image manifest. It is immutable, and it is the only thing worth signing. A tag such as `:latest` is a movable label.
- **Signature**: a cryptographic statement that "identity X vouches for digest D". It is stored in the registry next to the image (details below).
- **Sigstore / cosign**: cosign is the CLI that signs and verifies OCI artifacts. Sigstore is the surrounding infrastructure. **Fulcio** issues short-lived (minutes) X.509 certificates bound to an OIDC identity. **Rekor** is an append-only transparency log of signing events.
- **Keyless signing**: no long-lived private key. CI proves its identity with an OIDC token (for example a GitHub Actions workflow token), Fulcio issues a certificate for an ephemeral key, cosign signs, and the key is discarded.
- **Provenance**: a signed *attestation* saying how an artifact was built: source repo, commit, builder, build steps. It uses the in-toto statement format with the SLSA provenance predicate (`https://slsa.dev/provenance/v1`).
- **SLSA**: a framework that grades build integrity. Roughly, Build L1 means provenance exists, L2 means a hosted builder signs it, and L3 means the build is hardened so tenants cannot forge it. Check slsa.dev for the exact current wording.
- **Admission policy**: a Kubernetes admission controller (Kyverno, Sigstore policy-controller, Ratify and others) that verifies signatures before a pod is allowed to run.

## How it works
1. CI builds the image and pushes it. The registry returns a digest.
2. CI signs the **digest**, not the tag. cosign's own help text says to sign by digest "so that you actually sign what you think you're signing".
3. In keyless mode, cosign sends the OIDC token to Fulcio. The certificate it gets back embeds the workflow identity (a URI) and the issuer (`https://token.actions.githubusercontent.com` for GitHub Actions).
4. cosign signs, records the event in Rekor, and pushes the signature to the registry. In the classic scheme, the signature is an OCI artifact stored in the *same repository*, at a tag derived from the digest: `sha256-<hex>.sig`. Newer cosign can also use OCI 1.1 referrers (`--registry-referrers-mode oci-1-1`), which attach the signature to the image by a manifest reference instead of a tag.
5. A provenance attestation is attached the same way (`cosign attest` or a generator such as GitHub's attest action).
6. At deploy time, the verifier fetches the signature for the digest, validates the certificate chain, checks that the certificate identity and issuer match **what you expect**, and checks the transparency log entry.

```
CI job --OIDC token--> Fulcio --short-lived cert--> cosign sign <repo>@sha256:D
                                                        |
                          registry: repo@sha256:D  +  repo:sha256-D.sig
                                                        |
cluster admission --verify(identity, issuer, digest)----+
```

The trust moves from "who can push to the registry" to "which workflow identity is allowed to produce this digest".

## In production
A team signs every image in CI, and a Kyverno policy requires a valid signature before admission. After a registry credential leaks, an attacker pushes a backdoored image and repoints `api:prod` at it.

- **With the policy:** the pod is rejected with a "no matching signatures" style error. The new digest has no signature from the build workflow, so the admission webhook denies it.
- **What the team still checks:** they read the Rekor and registry history to see which digests were ever signed, then rotate the registry credential.
- **Provenance adds a second check:** a policy can also require that the attestation names the expected repo and builder. That catches a malicious or compromised *branch* that legitimately builds and signs an image from the wrong source.

## The gotcha
**A valid signature proves who signed, not that the signer is the right one.** In keyless mode, `cosign verify` refuses to run unless you pass `--certificate-identity` (or `-regexp`) and `--certificate-oidc-issuer` (or `-regexp`). That is by design, because any GitHub user can obtain a genuine Fulcio certificate. Teams that "make it work" with a loose regexp such as `--certificate-identity-regexp '.*'` have effectively disabled verification: an attacker's own signed image passes.

Pin the exact repo and workflow path, and ideally the ref (for example only `refs/heads/main` or release tags). A regexp should be anchored, for instance `^https://github.com/myorg/myrepo/\.github/workflows/release\.yml@refs/heads/main$`.

A second trap: if you verify by tag at deploy time, the tag may resolve to a different digest than the one you checked a minute earlier. Resolve to a digest once and deploy that.

## Try it
Needs `cosign` installed and a registry you control. Do not use a shared one. Key-pair mode is the simplest laptop demo, because keyless needs an OIDC identity.

```bash
docker run -d -p 5000:5000 --name reg registry:2
docker pull alpine:3.20 && docker tag alpine:3.20 localhost:5000/demo:v1
docker push localhost:5000/demo:v1
DIGEST=$(docker inspect --format '{{index .RepoDigests 0}}' localhost:5000/demo:v1)

cosign generate-key-pair                       # creates cosign.key / cosign.pub
cosign sign --key cosign.key --tlog-upload=false "$DIGEST"
cosign verify --key cosign.pub --insecure-ignore-tlog=true "$DIGEST"

# See where the signature lives: look for a tag shaped sha256-<hex>.sig
curl -s localhost:5000/v2/demo/tags/list
```

Look for the `.sig` tag in the tag list. The flags for a local registry or newer cosign versions may differ, so check `cosign sign --help` for your version. For keyless in CI, the verify form is:

```bash
cosign verify \
  --certificate-identity "https://github.com/myorg/myrepo/.github/workflows/release.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  registry.example.com/myorg/api@sha256:<digest>
```

## Think about it
Your policy pins the signer identity to the `release.yml` workflow on `main`, and verification passes for an image whose provenance says it was built from a fork's commit. Using what each of the signature and the attestation actually claims, work out how that can happen and which extra check closes the gap.
