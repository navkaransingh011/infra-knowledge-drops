# Instance metadata service and the container hop limit

`INF-253` · Cloud architecture fundamentals › Cloud identity and credentials · Difficulty 2/3 · ~6 min

> **Why this matters:** Every AWS SDK on an EC2 instance quietly fetches its IAM role credentials from a link-local HTTP endpoint. When a workload moves from the host into a container, that call can start timing out, and the error usually reads like an IAM problem.

*Note: this lesson is AWS EC2-specific. The AWS docs host was unreachable from the writing environment, so the details below are limited to well-established IMDSv2 behavior. Confirm defaults against the current EC2 User Guide before relying on them.*

## The moving parts
- **Instance Metadata Service (IMDS):** an HTTP service at `http://169.254.169.254/` that is reachable only from the instance itself. It serves instance facts and, if a role is attached, temporary IAM credentials.
- **Instance profile / role credentials:** short-lived keys that IMDS serves under `/latest/meta-data/iam/security-credentials/<role-name>`. SDKs refresh them automatically.
- **IMDSv1 vs IMDSv2:** v1 is a plain GET. v2 is session-oriented: you first `PUT` for a token, then present that token on every later request.
- **Hop limit:** the IP TTL set on the *token response packet*. It is a per-instance setting (`HttpPutResponseHopLimit`).

## How it works
IMDSv2 was designed to blunt SSRF. A vulnerable web app that is tricked into fetching a URL usually can only issue a simple GET. It can't send a `PUT` with a custom header, and it can't forward the response properly.

```
app ──PUT /latest/api/token  (X-aws-ec2-metadata-token-ttl-seconds: 21600)──▶ IMDS
app ◀── token (IP packet TTL = hop limit) ─────────────────────────────────── IMDS
app ──GET /latest/meta-data/... (X-aws-ec2-metadata-token: <token>) ─────────▶ IMDS
```

The causal chain:
1. The client sends a `PUT` to `/latest/api/token` with a TTL header (1 to 21600 seconds).
2. IMDS returns the token, and sets the IP TTL on that response to the configured hop limit.
3. Each router hop decrements the TTL, and a packet that reaches 0 is dropped.
4. A process on the host sees the response arrive after one hop, so a limit of 1 works.
5. A container on a bridge network (for example Docker's default) sits behind the host's virtual network namespace. The host forwards the packet, which counts as an extra hop. With a limit of 1 the response dies before the container receives it.
6. The client sees a timeout, not an HTTP error, and the SDK falls through its credential chain.

## In production
Setup: a service runs fine as a systemd unit on EC2, using its instance role to read S3. The team containerizes it and runs it with default bridge networking on the same instance type.

Symptoms: the container starts, and then every AWS call fails with something like `NoCredentialProviders` or `Unable to locate credentials`. The IAM role and policy are unchanged, and CloudTrail shows no denied calls, because the requests never get signed.

Diagnosis: from the host, the token `PUT` succeeds. From inside the container, the same `curl` hangs until it times out. That asymmetry points at the network path, not at permissions.

Fix, either of:
- Raise the hop limit on the instance to 2 (this is the usual approach).
- Run the container with host networking, which removes the extra hop.

Consider whether you want containers on the instance to reach the instance role at all. Raising the hop limit also lets any container on the box obtain the node's credentials. On shared nodes, prefer per-workload identity instead (for example IAM roles for service accounts or Pod Identity on EKS).

## The gotcha
The hop limit applies to the **token response**, not to later metadata GETs. So the failure happens at the very first step, which makes it look like "IMDS is blocked". Engineers who know that IMDSv2 is enabled often check for `HttpTokens=required`, see it is correct, and stop there. The real knob is `HttpPutResponseHopLimit`.

A second trap: setting the limit to a large value "to be safe" re-opens exposure. Anything that can route a packet from a few hops away, such as a proxy container, can then get a token.

## Try it
On an EC2 instance (throwaway, with an attached role if you want to see credentials):

```bash
# From the host: fetch a token, then use it
TOKEN=$(curl -s -X PUT http://169.254.169.254/latest/api/token \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id

# Same call from a container on the default bridge network
docker run --rm curlimages/curl -s -m 3 -X PUT \
  http://169.254.169.254/latest/api/token \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 60"

# Inspect, then change, the instance setting
aws ec2 describe-instances --instance-ids <id> \
  --query 'Reservations[].Instances[].MetadataOptions'
aws ec2 modify-instance-metadata-options --instance-id <id> \
  --http-put-response-hop-limit 2 --http-endpoint enabled
```

Look for: the host call returns a token, the container call hangs when the hop limit is 1, and it succeeds after you set it to 2. `MetadataOptions` should show `HttpPutResponseHopLimit`.

## Think about it
The token request is a `PUT`, and its response travels back across the network with a TTL. If you wanted to stop a compromised container from stealing the node's role credentials without breaking other containers, which part of this chain could you cut, and what would each choice break?
